# Jyotish AI — Threat Model

Repository: `fiahtfth/jyotish-ai`. Infrastructure: `render.yaml` (in repo) + Neon Postgres. No separate infrastructure repository exists; the model is built from the code and `render.yaml`.

## System overview and trust boundaries
A single Render free-tier Python web service (`render.yaml`) runs FastAPI (`backend/app/main.py`) and serves the statically exported Next.js frontend (`frontend/out`) via a catch-all SPA route. Persistent data is in Neon Postgres (`JYOTISH_DATABASE_URL`; SQLite `backend/jyotish.db` only for local dev). Chat replies are generated by external LLM APIs (Gemini, with Groq/OpenRouter fallbacks) or an offline deterministic responder (`backend/app/llm/providers.py`).

Trust boundaries:
1. Internet browser ↔ FastAPI (`/api/*`, bearer JWT in `Authorization`, token stored in `localStorage`).
2. FastAPI ↔ Neon Postgres (SQLAlchemy ORM).
3. FastAPI ↔ third-party LLM APIs (chart facts, analysis and chat history leave the system; gated by `JYOTISH_LLM_EXTERNAL_CONSENT`, set `true` in prod).
4. Render dashboard / env vars (secrets: `JYOTISH_JWT_SECRET` generated by Render, LLM API keys, DB URL).

## Entry points and who can reach them
- Anonymous: `POST /api/auth/register` (open signup), `POST /api/auth/login`, `GET /api/health`, SPA static files `/{path}`.
- Any authenticated user (own data only, scoped by `current_user`): `/api/auth/me` (GET/DELETE), `/api/geo/search`, `/api/profile` (GET/PUT), `/api/chat/{history,send,reset}`, `/api/chart/{varga}`, `/api/calibration`.
- No admin or multi-tenant roles exist; each user has one profile and one conversation.

## Assets and data sensitivity
- Account credentials (email, bcrypt password hash) and JWTs (HS256, 168h expiry, no revocation).
- Birth details (exact date/time/place, lat/long) — sensitive PII usable for identity verification.
- Chat history and calibration answers (personal life events: career, marriage, health).
- LLM API keys and free-tier quota; Neon DB credentials; `JYOTISH_JWT_SECRET`.

## Attacker profiles
- Anonymous internet attacker (public site, open signup).
- Registered user attempting to access or modify other users' data (IDOR, token forgery).
- Chat user attempting prompt injection against the LLM (leak system prompt, bypass the prediction gate, abuse quota).
- Supply-chain risk via unpinned Python dependencies.

## Existing controls
- bcrypt password hashing (passlib, `bcrypt==4.0.1`); JWT HS256 with Render-generated secret in prod.
- All data routes resolve the user from the token; no user-supplied IDs on data routes.
- Pydantic validation on inputs (`ChatIn` max 4000 chars, profile field bounds).
- Per-user in-memory chat rate limit (30/min, `_rate_limit`); not applied to auth endpoints.
- Prediction gate enforced in code, not the prompt (`orchestrator._open_turn`).
- External-LLM consent gate; OpenRouter limited to free models.
- SPA path traversal guard; `Cache-Control: no-store` on `/api/*`; CORS restricted to configured origins.

## Out of scope / accepted risk
User-confirmed (2026-11-17): every asset above matters equally and every attacker profile matters.
- Out of scope (user): accuracy or tone of astrology answers (content quality of LLM/offline replies, calculation correctness) — not a security concern.
- Nothing else is out of scope: DoS on the free tier, demo accounts, and local-dev defaults remain in scope.
